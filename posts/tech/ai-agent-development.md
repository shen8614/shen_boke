    14|# AI Agent 开发实践：从概念到落地
    15|
    16|## 什么是 AI Agent
    17|
    18|2025 年开始，AI Agent 这个词被用得太多了，多到几乎失去意义。但它的核心概念其实很简单：一个能自主决策、调用工具、完成任务的 AI 程序。和普通的 LLM 对话不同，Agent 有"手"——它能读写文件、执行命令、调用 API、甚至操作浏览器。它也有"记忆"——能在多轮交互中记住上下文，根据中间结果调整策略。
    19|
    20|我从 2025 年初开始折腾 AI Agent，从最简单的 ReAct 模式到现在的多智能体系统，记录一下关键经验和踩坑。
    21|
    22|## Agent 的基本架构
    23|
    24|一个最小可用的 Agent 需要三个组件：
    25|
    26|```mermaid
    27|graph TD
    28|    USER[用户任务] --> LLM[LLM 大脑]
    29|    LLM -->|思考 + 决策| ACT[行动]
    30|    ACT --> TOOL[调用工具]
    31|    TOOL -->|返回结果| OBS[观察结果]
    32|    OBS -->|反馈| LLM
    33|    LLM -->|任务完成| RESULT[输出结果]
    34|
    35|    style LLM fill:#4a9eff,color:#fff
    36|    style TOOL fill:#ff9f43,color:#fff
    37|    style OBS fill:#2ed573,color:#fff
    38|```
    39|
    40|1. **LLM 大脑** — 负责理解任务、推理、决策
    41|2. **工具集** — Agent 可以调用的能力（搜索、代码执行、文件操作等）
    42|3. **循环机制** — 观察环境 → 思考 → 行动 → 观察结果 → 继续思考
    43|
    44|这就是经典的 ReAct（Reasoning + Acting）模式。LLM 每次输出一个"思考"和一个"动作"，系统执行动作后把结果返回给 LLM，如此循环直到任务完成。
    45|
    46|```python
    47|# 简化的 ReAct 循环
    48|def agent_loop(task, tools, llm):
    49|    messages = [{"role": "user", "content": task}]
    50|    
    51|    while True:
    52|        response = llm.chat(messages, tools=tools)
    53|        
    54|        if response.has_tool_calls():
    55|            for call in response.tool_calls:
    56|                result = execute_tool(call.name, call.arguments)
    57|                messages.append({"role": "tool", "content": result})
    58|        else:
    59|            return response.content  # 任务完成
    60|```
    61|
    62|看起来很简单对吧？真正动手后你会发现，魔鬼全在细节里。
    63|
    64|## 踩坑记录
    65|
    66|### 坑 1：工具描述决定成败
    67|
    68|Agent 调用工具完全依赖你写的工具描述（tool description）。描述写得模糊，Agent 就会乱调。我曾经给一个文件搜索工具写了这样的描述：
    69|
    70|```
    71|description: "搜索文件"
    72|```
    73|
    74|结果 Agent 在需要读取文件内容时也调用了这个工具，因为它以为"搜索"就是"查找并读取"。改成下面这样就好了：
    75|
    76|```
    77|description: "按文件名模式搜索文件路径，返回匹配的文件列表。不搜索文件内容。如需读取文件请使用 read_file 工具。"
    78|```
    79|
    80|**教训**：工具描述要写得像给一个新来的实习生解释一样——精确、有边界、有示例。
    81|
    82|### 坑 2：上下文窗口是硬约束
    83|
    84|Agent 的每轮循环都会往消息列表里追加内容（思考过程、工具调用、工具返回结果）。一个复杂任务可能跑 20-30 轮，消息长度轻松超过模型的上下文窗口。
    85|
    86|解决方案有几种：
    87|- **摘要压缩**：定期让 LLM 总结之前的对话，用摘要替代原始消息
    88|- **滑动窗口**：只保留最近 N 轮的完整消息，更早的用摘要
    89|- **外部记忆**：把关键信息存到向量数据库，需要时检索
    90|
    91|我最终用的是滑动窗口 + 关键信息提取的组合。每 10 轮做一次压缩，把重要的决策和中间结果提取出来存到 system message 里。
    92|
    93|### 坑 3：Agent 会"跑偏"
    94|
    95|给 Agent 一个模糊的任务，它可能往完全错误的方向一路狂奔。比如你说"优化这个函数的性能"，它可能花 20 分钟重写了整个模块的架构，引入了一堆你不需要的缓存和异步逻辑。
    96|
    97|解决方法是**拆分任务 + 约束边界**。不要给 Agent 一个大而模糊的目标，而是拆成具体的子任务，每个子任务明确输入、输出和约束条件。
    98|
    99|### 坑 4：错误处理比成功路径更重要
   100|
   101|Agent 的正常路径通常很好写，但错误处理才是真正的挑战。工具调用失败怎么办？LLM 输出了不可解析的格式怎么办？执行超时怎么办？
   102|
   103|我的经验是给每个工具调用都加超时和重试机制，LLM 输出解析失败时自动重试（最多 3 次），连续失败 3 次就终止并返回错误信息。宁可失败得干净，也不要让 Agent 在错误状态上越跑越远。
   104|
   105|## 多智能体协作
   106|
   107|单个 Agent 处理复杂任务时容易"超载"——上下文太长、工具太多、决策太复杂。多智能体模式把一个大任务拆给多个专门的 Agent 协作完成。
   108|
   109|常见的模式有：
   110|
   111|- **主管-工人模式**：一个主管 Agent 负责任务拆解和调度，多个工人 Agent 各自执行具体任务
   112|- **流水线模式**：Agent A 的输出作为 Agent B 的输入，依次处理
   113|- **辩论模式**：多个 Agent 对同一个问题给出不同方案，最后投票或由裁判 Agent 选择
   114|
   115|我实际用得最多的是主管-工人模式。比如让主管 Agent 分析需求、拆成子任务、分配给"前端 Agent"和"后端 Agent"各自执行，最后主管汇总结果。这种方式比单个 Agent 啥都干效率高很多。
   116|
   117|## 现成的 Agent 框架
   118|
   119|2026 年主流的 Agent 框架：
   120|
   121|| 框架 | 特点 | 适合场景 |
   122||------|------|----------|
   123|| LangChain | 生态最大，工具最全 | 快速原型、复杂链路 |
   124|| CrewAI | 多智能体协作开箱即用 | 团队协作场景 |
   125|| AutoGen | 微软出品，对话式多 Agent | 研究、复杂推理 |
   126|| Claude Code | 终端 Agent，直接操作项目 | 代码开发、文件操作 |
   127|| OpenAI Codex | 云端 Agent，沙箱执行 | 代码生成、自动化 |
   128|
   129|如果你是做应用开发，LangChain 或 CrewAI 上手最快。如果你是写代码为主，Claude Code 或 Codex 这类"代码 Agent"更实用。
   130|
   131|## 什么时候该用 Agent，什么时候不该
   132|
   133|Agent 不是万能的。它适合的场景：
   134|- 任务步骤不确定，需要动态决策
   135|- 需要调用多个外部工具或 API
   136|- 任务有分支逻辑，不能线性执行
   137|
   138|不适合的场景：
   139|- 任务步骤固定且明确 → 直接写代码
   140|- 对延迟敏感 → Agent 的多轮循环太慢
   141|- 对成本敏感 → Agent 消耗大量 token
   142|
   143|一个判断标准：如果你能把任务写成一个 if-else 流程图，就不要用 Agent。Agent 的价值在于处理那些你画不出流程图的不确定性。
